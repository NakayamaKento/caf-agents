## 1. エグゼクティブサマリー

### 1.1 運用モデル選択の目的と背景

本文書は、Azure Cloud Adoption Framework（CAF）計画フェーズ（Plan Methodology）の**ステップ 2「クラウド運用モデルの選択」**として策定されます。

戦略フェーズで確立した組織評価（総合スコア 2.6/5.0）と、計画フェーズ ステップ 1 の導入体験マッピングの結果を踏まえ、組織が採用すべきクラウド運用モデルを決定します。運用モデルの選択は、クラウド導入の速度・品質・リスク管理の三点に根本的な影響を与えるため、早期に確立することが不可欠です。

### 1.2 評価前提：現状の組織スナップショット

| 評価項目 | 現状値 | 意味するインパクト |
|---|---|---|
| **組織総合スコア** | 2.6 / 5.0 | 移行前期段階。体系的な運用モデル確立が急務 |
| **ガバナンス成熟度** | Level 2（管理済み） | ポリシー基盤はあるが自動化が未整備 |
| **文化的準備度** | 2.0 / 5.0 | 変革への抵抗リスクが高い |
| **技術的準備度** | 1.5 / 5.0 | IaC・自動化スキルが最大のボトルネック |
| **プロセス成熟度** | 2.0 / 5.0 | ITSM あるが分散・属人化 |
| **現IT部門規模** | 50名程度 | クラウド専任体制は別途確保が必要 |
| **DC契約満了** | FY2026 Q3（2026年9月） | タイムプレッシャーが大きい |

## 2. 運用モデルの選択肢評価

### 2.1 Azure CAF が定義する 4 つの運用モデル

Azure CAF では、組織の規模・成熟度・文化に応じた 4 つの運用モデルを定義しています。
各モデルを組織の現状と照合して評価します。

---

#### モデル A：一元化モデル（Centralized IT）

```
┌─────────────────────────────────────────────────┐
│              中央 IT チーム                       │
│  （すべてのクラウドリソースを集中管理）               │
└──────────────────┬──────────────────────────────┘
                   │ すべての依頼・変更を一元処理
        ┌──────────┼──────────┐
        │          │          │
   事業部 A     事業部 B    事業部 C
  （リクエスト）（リクエスト）（リクエスト）
```

**概要**: 全クラウドリソースを中央の IT チームが一元管理。事業部門はリクエストベースでサービスを利用。

| 観点 | 評価 | 詳細 |
|---|---|---|
| **ガバナンス制御** | ◎ 非常に高い | ポリシー適用・コスト管理が容易 |
| **セキュリティ** | ◎ 非常に高い | 統一されたセキュリティポリシー適用 |
| **スピード** | ✕ 非常に低い | 中央チームがボトルネックになる |
| **スケーラビリティ** | ✕ 低い | チーム規模の限界が全体の上限 |
| **イノベーション** | ✕ 低い | 事業部門の自律性が制約される |
| **組織適合性** | △ やや低い | 現状の IT 文化（集権型）には馴染むが、変革に不向き |

**メリット**:
- 統制・コンプライアンス管理が最もシンプル
- コスト管理（一元請求・配賦）が容易
- スキルを中央に集中できる（人材効率が高い）

**デメリット**:
- クラウドの速度・アジリティのメリットを享受できない
- 中央チームへの依存度が高く、単一障害点になる
- 事業部門のデジタル変革意欲を削ぐ可能性がある
- FY2026 Q3 の移行タイムラインには対応不可能（スピード不足）

---

#### モデル B：共有管理モデル（Shared Responsibility）

```
┌─────────────────────────────────────────────────┐
│              CCoE（共有サービス）                  │
│  ・プラットフォーム基盤（Landing Zone）             │
│  ・ガバナンスポリシー・標準化                       │
│  ・セルフサービスカタログ                           │
└──────────────────┬──────────────────────────────┘
            ガードレール内で自律運用
        ┌──────────┼──────────┐
        │          │          │
   ワークロードA  ワークロードB  ワークロードC
   チーム        チーム        チーム
  （自律デプロイ）（自律デプロイ）（自律デプロイ）
```

**概要**: CCoE が基盤・標準・ガードレールを提供し、各ワークロードチームが自律的にクラウドを活用。

| 観点 | 評価 | 詳細 |
|---|---|---|
| **ガバナンス制御** | ○ 高い | ポリシーベースのガードレールで統制 |
| **セキュリティ** | ○ 高い | ベースラインは CCoE が管理、詳細は各チーム |
| **スピード** | ◎ 非常に高い | ガードレール内で各チームが自律的に動ける |
| **スケーラビリティ** | ◎ 非常に高い | チーム数が増えても CCoE の負荷は低増加 |
| **イノベーション** | ◎ 非常に高い | 各チームの創意工夫が最大化される |
| **組織適合性** | ○ 高い | 目指すべき方向性と整合 |

**メリット**:
- クラウドのアジリティとガバナンスのバランスが最適
- セルフサービス化によりスケーラビリティが高い
- チームの自律性が高まり、組織変革を推進
- Azure CAF が明示的に推奨するモデル

**デメリット**:
- CCoE の立ち上げ・能力構築に時間とコストが必要
- ガードレールの設計ミスがセキュリティ・コストリスクになる
- ワークロードチームのクラウドスキルが前提条件

---

#### モデル C：分散型モデル（Decentralized / Business-led）

```
事業部 A     事業部 B     事業部 C
┌───────┐   ┌───────┐   ┌───────┐
│独自IT │   │独自IT │   │独自IT │
│クラウド│   │クラウド│   │クラウド│
│管理   │   │管理   │   │管理   │
└───────┘   └───────┘   └───────┘
   ↑              ↑            ↑
（最小限の中央ガイドラインのみ）
```

**概要**: 各事業部門が独自にクラウドを調達・管理。中央 IT は最小限のガイドライン提供のみ。

| 観点 | 評価 | 詳細 |
|---|---|---|
| **ガバナンス制御** | ✕ 非常に低い | 統制が効かず「シャドー IT」が蔓延 |
| **セキュリティ** | ✕ 非常に低い | セキュリティポリシーの不統一 |
| **スピード** | ◎ 非常に高い | 各部門が完全自律で動ける |
| **スケーラビリティ** | △ 中程度 | 部門間の重複投資・断片化が問題 |
| **イノベーション** | ○ 高い | 部門の自由度は高い |
| **組織適合性** | ✕ 低い | 現状のクラウドスキル不足では機能しない |

**メリット**:
- 事業部門の意思決定速度が最大化
- イノベーション実験が容易

**デメリット**:
- コスト爆発・セキュリティインシデントのリスクが極めて高い
- コンプライアンス違反のリスクが高い（個人情報保護法・ISMAP 等）
- スキル不足の組織では機能しない
- 中央 IT 部門の価値が失われる

---

#### モデル D：ハイブリッドモデル（Hybrid / Federated）

```
┌─────────────────────────────────────────────────┐
│     中央 IT / CCoE（基盤・統制・セキュリティ）      │
│  ・ネットワーク接続（Hub-Spoke）                   │
│  ・ID 管理（Entra ID）                            │
│  ・コンプライアンスポリシー（Azure Policy）         │
│  ・共有サービス（ログ収集・SIEM）                   │
└──────────────────┬──────────────────────────────┘
          ↕ 合意された境界内で協調
   ┌──────────────────────────────────┐
   │      事業部門 IT / ワークロードチーム  │
   │  ・アプリケーション開発・デプロイ      │
   │  ・コスト管理（部門予算範囲内）        │
   │  ・ワークロード固有の監視・運用        │
   └──────────────────────────────────┘
```

**概要**: 中央 IT が基盤・統制を担い、事業部門が合意された境界内でアプリケーションを自律管理。

| 観点 | 評価 | 詳細 |
|---|---|---|
| **ガバナンス制御** | ○ 高い | 基盤レイヤーは中央管理、アプリレイヤーは分散 |
| **セキュリティ** | ○ 高い | 中央でセキュリティベースラインを強制適用 |
| **スピード** | ○ 高い | アプリ開発は事業部門が自律的に実施 |
| **スケーラビリティ** | ○ 高い | 境界が明確なため役割分担がスケール |
| **イノベーション** | ○ 高い | 事業部門の自律性を確保しながらガバナンス維持 |
| **組織適合性** | ◎ 非常に高い | 現状からの段階的移行が可能 |

**メリット**:
- 基盤統制とアプリ自律性を両立
- 段階的な権限委譲が可能（成熟度に応じて移行可能）
- 既存の IT 組織を活かせる
- Azure CAF の「エンタープライズスケール Landing Zone」に最も適合

**デメリット**:
- 境界設計が複雑（責任の曖昧地帯が生まれやすい）
- 中央と事業部門の調整コストが発生
- 「中央が何を管理し、何を委譲するか」の合意形成が必要

---

## 3. 推奨運用モデルの選定

### 3.1 推奨モデル：ハイブリッド連邦モデル（Hybrid Federated Model）

> **推奨**: **モデル D「ハイブリッド連邦モデル」**を採用します。
> ただし、フェーズ 1 では一時的に中央集権型の CCoE 主導で運用し、
> 段階的にハイブリッド連邦モデルへ移行します。

評価スコア最高の 4.03 であることに加え、以下の定性的根拠により推奨します。

### 3.2 選定理由の詳述

#### 根拠 1：組織スコア 2.6/5.0 が示す「管理された移行」の必要性

技術的準備度 1.5/5.0、文化的準備度 2.0/5.0 という評価は、完全分散型（モデル C）への即時移行が実質不可能であることを示しています。一方、一元化モデル（モデル A）では FY2026 Q3 のタイムラインに対応できません。ハイブリッドモデルは「段階的な権限委譲」を設計の中心に置くため、現状のスキルギャップを埋めながら移行を進められます。

#### 根拠 2：@cloud-governance のガバナンス要件との整合

ガバナンス成熟度 Level 2（管理済み段階）では、Azure Policy を Deny モードで適用するには基盤整備が必要です。ハイブリッドモデルでは：

- **中央 CCoE が管理する層**: Azure Policy（Deny モード）、Entra ID、Hub ネットワーク、Log Analytics ワークスペース
- **事業部門が管理する層**: アプリケーション設定、ワークロード固有リソース、部門予算範囲内のスケーリング

この二層構造により、@cloud-governance は確実なポリシー適用を実現しながら、@cloud-platform はセルフサービスカタログを通じたワークロードチームの自律性を確保できます。

#### 根拠 3：@cloud-operations の運用能力に基づく実現可能性評価

```
運用能力の現状評価（@cloud-operations 視点）:

監視成熟度: Level 1-2（基本的な監視のみ）
SLO 定義: 未整備
インシデント対応: ITSM あるが手動主体
自動化率: < 10%

→ フェーズ1では CCoE が中央で監視基盤を構築・運用し、
  フェーズ2以降で段階的にワークロードチームへ権限委譲
```

@cloud-operations の評価によれば、現時点でワークロードチームに完全な運用責任を委譲することは過大な負荷になります。ハイブリッドモデルの段階的移行アプローチが唯一の実現可能な選択です。

#### 根拠 4：Azure CAF エンタープライズスケール Landing Zone との整合

Microsoft が推奨する「Enterprise-Scale Landing Zone（ESLZ）」のリファレンスアーキテクチャは、ハイブリッド連邦モデルを前提に設計されています。

```
Management Group 階層（ESLZ）
Root Management Group
├── Platform（CCoE 管理）
│   ├── Identity（Entra ID）
│   ├── Connectivity（Hub VNet）
│   └── Management（Log Analytics, Policy）
└── Landing Zones（各チーム管理）
    ├── Corp（社内ワークロード）
    ├── Online（公開ワークロード）
    └── Sandbox（実験・検証）
```

この階層構造は本推奨モデルと完全に一致しています。

## 4. CCoE 中心の運用体制定義

### 4.1 CCoE の役割と責任の詳細

CCoE は「ゲートキーパー」ではなく「イネーブラー」として機能します。CCoE が管理するリソースと、ワークロードチームに委譲するリソースを明確に分離します。

#### CCoE が直接管理するリソース（Platform Layer）

| リソースカテゴリ | 具体的なリソース | 変更権限 | 理由 |
|---|---|---|---|
| **ID・アクセス管理** | Entra ID テナント、管理グループ RBAC | CCoE のみ | 特権管理の集中 |
| **ネットワーク基盤** | Hub VNet、ExpressRoute、Azure Firewall、Private DNS Zone | CCoE のみ | セキュリティ境界の統一管理 |
| **ガバナンスポリシー** | Azure Policy（Deny モード）、Azure Blueprints | CCoE のみ（@cloud-governance 主導） | 統制の一貫性確保 |
| **監視基盤** | 中央 Log Analytics ワークスペース、Azure Monitor、Sentinel | CCoE のみ（@cloud-operations 主導） | セキュリティ可視化の一元化 |
| **セキュリティ基盤** | Defender for Cloud、Key Vault（共有）、Entra ID PIM | CCoE のみ（@cloud-security 主導） | セキュリティベースライン統一 |
| **コスト管理** | Management Group 予算アラート、Cost Management ポリシー | CCoE のみ（@cloud-governance 主導） | コスト爆発防止 |

#### ワークロードチームが管理するリソース（Application Layer）

| リソースカテゴリ | 具体的なリソース | 変更権限 | 条件 |
|---|---|---|---|
| **アプリケーション基盤** | App Service、AKS、Functions、SQL Database 等 | ワークロードチーム | CCoE テンプレートを使用すること |

| **ワークロード固有 Key Vault** | アプリ専用シークレット管理 | ワークロードチーム | CCoE のポリシー（Private Endpoint 必須等）に準拠 |
| **CI/CD パイプライン** | GitHub Actions / Azure DevOps パイプライン | ワークロードチーム | CCoE テンプレートを基盤に使用 |
| **部門予算範囲内のスケーリング** | 自動スケール設定、リソース SKU 変更 | ワークロードチーム | 予算アラート閾値内であること |

### 4.2 各チームとの連携方法

#### 意思決定・エスカレーションパス

```

  └─ 所要時間: 即時〜1 営業日

  └─ ワークロードチーム → CCoE（メール/チケット）→ 承認

  └─ ワークロードチーム → CCoE → エグゼクティブスポンサー
```

## 付録 B：主要意思決定記録（ADR）

### ADR-0001: ハイブリッド連邦モデルの採用

**ステータス**: Accepted（2026年4月12日）

**コンテキスト**: 組織総合スコア 2.6/5.0、FY2026 Q3 のデータセンター契約満了という制約条件下で、クラウド運用モデルを選択する必要があった。

**決定**: ハイブリッド連邦モデル（モデル D）を採用し、フェーズ 1 では一時的に中央集権型 CCoE 主導で運用する。

**根拠**:
- 加重スコアリングで最高スコア（4.03/5.0）
- Azure CAF エンタープライズスケール Landing Zone との整合性
- 段階的移行が可能であり、現状のスキルギャップを考慮した現実的な選択
- @cloud-governance と @cloud-operations の評価結果と整合

**影響**:
- @cloud-platform: Landing Zone をエンタープライズスケール設計で構築すること
- @cloud-security: セキュリティポリシーは CCoE が中央管理すること
- @cloud-governance: Policy as Code の導入を優先すること
- @cloud-operations: 監視基盤は中央集権型から開始し、段階的に委譲すること

**関連する ADR**: ADR-0002（Landing Zone 設計）、ADR-0003（外部パートナー選定）

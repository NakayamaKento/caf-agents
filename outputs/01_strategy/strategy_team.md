# クラウド戦略チーム定義書
**Azure Cloud Adoption Framework (CAF) 準拠**
**バージョン: 1.0.0 | 作成日: 2025年 | 分類: 組織内機密**

---

## 1. エグゼクティブサマリー

### 目的

本定義書は、Azure Cloud Adoption Framework (CAF) に基づくクラウド導入を成功に導くため、
組織内に設置すべき戦略チームの構造・役割・責任・連携方法を定義するものです。
クラウド導入は単なる技術移行ではなく、組織の働き方・意思決定・文化変革を伴う
**エンタープライズ変革プログラム**として位置づけます。

### 背景と課題認識

クラウド導入が失敗する主要原因の上位は「技術的な問題」ではなく、
「組織・ガバナンス・人材の問題」であることが各調査で示されています。

| 失敗要因 | 比率（参考値） |
|---|---|
| 組織・チーム体制の未整備 | 約 35% |
| ガバナンス・コンプライアンスの未整備 | 約 25% |
| スキル・人材不足 | 約 20% |
| 技術的な問題 | 約 15% |
| その他 | 約 5% |

### 本定義書が目指すもの

- **明確な役割と責任の確立**: RACI マトリックスによる責任の可視化
- **迅速な意思決定**: エスカレーションパスの標準化によるボトルネック解消
- **セルフサービスの実現**: CCoE を中心とした自律的なクラウド利用体制の構築
- **継続的な成熟度向上**: 段階的なチーム成長ロードマップの実践

### 適用範囲

本定義書は、クラウド導入に関与するすべての組織単位（IT 部門・事業部門・経営層）に適用されます。

## 2. Azure CAF チーム構造

### CAF が推奨する 5 つのチーム機能

Azure CAF は、クラウド導入を組織的に成功させるために、以下の 5 つのチーム機能を推奨しています。
これらは独立したチームである必要はなく、既存の組織構造に機能として組み込むことも可能です。

```
┌─────────────────────────────────────────────────────────────────┐
│                     経営層・ステークホルダー                        │
└──────────────────────────────┬──────────────────────────────────┘
                               │ 戦略的方向性
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│              Cloud Strategy Team（クラウド戦略チーム）              │
│         ビジネス目標とクラウド導入の整合性を確保する意思決定機関         │
└──────┬──────────────────────────────────────────────┬───────────┘
       │ ガバナンス方針                                   │ 採用優先順位
       ▼                                               ▼
┌──────────────────┐                    ┌──────────────────────────┐
│  Cloud Governance │                    │    Cloud Adoption Team   │
│  Team             │◀───連携────────────│   （クラウド導入チーム）    │
│ （ガバナンスチーム）│                    │  ワークロードの移行・実装  │
└──────────────────┘                    └──────────────────────────┘
       ▲                                               ▲
       │                                               │
       └──────────────┬────────────────────────────────┘
                      │ 標準・ガイドライン・テンプレート提供
                      ▼
┌─────────────────────────────────────────────────────────────────┐
│           Cloud Center of Excellence（CCoE）                     │
│         プラットフォーム基盤・標準化・セルフサービス推進機関            │
│   @cloud-platform + @cloud-security + @cloud-governance 統合     │
└──────────────────────────────┬──────────────────────────────────┘
                               │ 標準運用手順・監視基盤
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│              Cloud Operations Team（クラウド運用チーム）             │
│         本番環境の安定稼働・SLO 管理・インシデント対応機関              │
└─────────────────────────────────────────────────────────────────┘
```

### 各チームの概要

| チーム機能 | 主目的 | 主な関与者 | エージェント対応 |
|---|---|---|---|
| **Cloud Strategy Team** | ビジネス目標の設定と ROI 測定 | CxO、事業部門長、IT 部門長 | `@cloud-strategy` |
| **Cloud Adoption Team** | ワークロードの移行・開発・実装 | アプリ開発者、インフラエンジニア | `@cloud-platform` |
| **Cloud Governance Team** | ポリシー・コンプライアンス・コスト管理 | ガバナンス担当、セキュリティ担当 | `@cloud-governance` |
| **Cloud Center of Excellence** | 標準化・セルフサービス・プラットフォーム | プラットフォームエンジニア全員 | `@ccoe` |
| **Cloud Operations Team** | 監視・運用・インシデント対応 | SRE、運用担当 | `@cloud-operations` |

> **注記**: Azure CAF の 5 機能チームに加え、本組織では `@cloud-security` を独立したセキュリティ
> 専門機能として設置し、すべてのチームのセキュリティ要件を横断的にサポートします。

## 3. チームメンバーと役割定義

> ⚠️ **人員規模に関する重要注意事項**
> 
> 以下に示す「推奨人員構成」は各チームの**成熟期（フェーズ3: 12〜24ヶ月後）**における目標構成です。
> 組織の IT 部門が全体 50 名程度の場合、全チームの合計（最大 37 名）は現実的ではありません。
> 
> **フェーズ別スタート推奨構成（IT 部門 50 名想定）:**
> 
> | フェーズ | 期間 | コア人員 | 外部パートナー | 備考 |
> |---|---|---|---|---|
> | フェーズ1（立ち上げ） | 0〜6ヶ月 | **6〜8名（専任）** | 10〜15名 | CCoE コア + 移行リード |
> | フェーズ2（拡大） | 7〜18ヶ月 | **12〜15名（専任）** | 5〜10名 | 各チームに 2〜3 名配置 |
> | フェーズ3（成熟） | 19ヶ月〜 | **20〜25名（専任）** | 必要に応じて | 目標構成に近づく |
> 
> **既存業務との兼任ルール:**
> - フェーズ1〜2 では、各エンジニアが現行業務（オンプレ保守）との兼任を前提とする
> - 専任化は段階的に進め、オンプレ業務は外部委託で対応する
> - CCoE コア 6 名は Day1 から専任とする（最低条件）

### 3.1 Cloud Strategy Team（クラウド戦略チーム）
**対応エージェント: `@cloud-strategy`**

#### チームミッション

> 「ビジネス戦略とクラウド導入の完全な整合性を確保し、投資対効果を最大化するとともに、
> 組織全体のクラウドジャーニーの方向性を定義・監督する」

#### 主要責任

| 責任領域 | 具体的な活動 | 成果物 |
|---|---|---|
| **戦略策定** | クラウド導入動機の定義、ビジネスケース作成 | クラウド戦略文書、ビジネスケース |
| **投資管理** | 予算計画、ROI 測定、投資優先順位付け | 投資計画書、ROI レポート |
| **ロードマップ** | 導入フェーズ計画、マイルストーン設定 | クラウド導入ロードマップ |
| **ステークホルダー管理** | 経営層への報告、部門間調整 | エグゼクティブダッシュボード |
| **成果測定** | KPI モニタリング、価値実現の追跡 | 月次進捗レポート |

#### 必要スキルセット

- **必須**: ビジネス戦略立案、財務分析（TCO/ROI）、経営層とのコミュニケーション
- **推奨**: クラウドの基礎知識（Azure Fundamentals 相当）、変革管理（チェンジマネジメント）
- **資格**: AZ-900（Azure Fundamentals）、MBA または同等の経営知識

#### 推奨人員構成

| 役割 | 人数 | 主な責任 |
|---|---|---|
| **クラウド戦略オーナー** (CTO / VP Engineering) | 1名 | 最終意思決定、経営層との連携 |
| **クラウド戦略マネージャー** | 1〜2名 | 日常的な戦略調整、ロードマップ管理 |
| **ビジネスアーキテクト** | 1〜2名 | ビジネス要件とクラウド機能のマッピング |
| **財務アナリスト** | 1名 | コスト分析、ROI 計算、予算管理 |
| **変革管理担当** | 1名 | 組織変革、トレーニング計画 |
| **合計** | **5〜7名** | |

#### エージェントとの対応

```
@cloud-strategy との連携:
  入力: ビジネス目標、予算制約、タイムライン要件
  出力: クラウド導入戦略、ROI 分析、優先順位付きロードマップ
  
  主要ユースケース:
  - "Azure 移行のビジネスケースを作成してほしい"
  - "競合他社と比較した場合のクラウド ROI を分析してほしい"
  - "経営層向けクラウド投資プレゼンテーションを作成してほしい"
```

### 3.2 Cloud Adoption Team（クラウド導入チーム）
**対応エージェント: `@cloud-platform`（技術実装側面）**

#### チームミッション

> 「定義された戦略とアーキテクチャ標準に基づき、ワークロードをクラウドへ移行・開発し、
> ビジネス価値を迅速かつ安全に実現する」

#### 主要責任

| 責任領域 | 具体的な活動 | 成果物 |
|---|---|---|
| **ワークロード移行** | 移行波計画、移行実行、移行後検証 | 移行完了レポート |
| **クラウドネイティブ開発** | IaC 実装、CI/CD パイプライン構築 | アプリケーション、インフラコード |
| **アーキテクチャ設計** | ソリューションアーキテクチャ設計、Well-Architected レビュー | アーキテクチャ設計書 |
| **技術検証** | PoC 実施、新技術評価 | PoC レポート、推奨事項 |
| **ナレッジ共有** | ベストプラクティス文書化、チーム教育 | 技術ガイド、教育資料 |

#### 必要スキルセット

- **必須**: Azure インフラ（仮想マシン、ネットワーク、ストレージ）、IaC（Terraform または Bicep）、CI/CD
- **推奨**: コンテナ（Docker/Kubernetes）、セキュリティ基礎、DevOps プラクティス
- **資格**: AZ-104（Azure Administrator）、AZ-204（Azure Developer）、AZ-305（Azure Solutions Architect）

#### 推奨人員構成

| 役割 | 人数 | 主な責任 |
|---|---|---|
| **クラウドアーキテクト** | 1〜2名 | アーキテクチャ設計、技術標準策定 |
| **クラウドエンジニア（インフラ）** | 2〜4名 | IaC 実装、Landing Zone 構築 |
| **クラウドエンジニア（アプリ）** | 2〜4名 | アプリケーション移行・開発 |
| **DevOps エンジニア** | 1〜2名 | CI/CD パイプライン、自動化 |
| **移行スペシャリスト** | 1〜2名（移行フェーズ限定）| 移行計画、ツール活用 |
| **合計** | **7〜14名** | ※ワークロード数に応じてスケール |

### 3.3 Cloud Governance Team（クラウドガバナンスチーム）
**対応エージェント: `@cloud-governance`**

#### チームミッション

> 「ポリシー・コンプライアンス・コスト管理を通じて、クラウド環境の秩序とリスク管理を確保し、
> ガードレールによってチームの自由度を守りながら組織を保護する」

#### 主要責任

| 責任領域 | 具体的な活動 | 成果物 |
|---|---|---|
| **ポリシー管理** | Azure Policy 定義、イニシアチブ管理 | ポリシーセット、コンプライアンスレポート |
| **RBAC 管理** | ロール設計、アクセス権レビュー | RBAC 設計書、定期アクセスレビュー |
| **コスト管理（FinOps）** | 予算設定、コスト配賦、最適化推奨 | コストレポート、最適化計画 |
| **コンプライアンス** | 規制要件マッピング、監査対応 | コンプライアンスマトリックス |
| **タグ戦略** | タグポリシー定義・適用 | タグ戦略文書 |

#### 必要スキルセット

- **必須**: Azure Policy、Azure RBAC、Microsoft Cost Management、コンプライアンス要件（ISMS/PCI DSS 等）
- **推奨**: Azure Landing Zone、Terraform Sentinel、FinOps 手法
- **資格**: AZ-500（Azure Security Technologies）、SC-900、FinOps Certified Practitioner

#### 推奨人員構成

| 役割 | 人数 | 主な責任 |
|---|---|---|
| **ガバナンスリード** | 1名 | ガバナンス戦略、ポリシーロードマップ |
| **クラウドポリシーエンジニア** | 1〜2名 | Policy as Code 実装・管理 |
| **FinOps アナリスト** | 1名 | コスト分析・最適化・レポーティング |
| **コンプライアンス担当** | 1名 | 規制対応、監査サポート |
| **合計** | **4〜5名** | |

### 3.4 Cloud Center of Excellence（CCoE）
**対応エージェント: `@ccoe`（統合調整）、`@cloud-platform`、`@cloud-security`、`@cloud-governance`**

#### チームミッション

> 「ゲートキーパーではなくイネーブラーとして機能し、標準化されたプラットフォーム・テンプレート・
> ガイドラインを通じて、すべての導入チームが自律的かつ安全にクラウドを活用できる環境を創る」

#### 主要責任

| 責任領域 | 具体的な活動 | 成果物 |
|---|---|---|
| **Landing Zone 管理** | 標準 Landing Zone の設計・管理・進化 | Landing Zone テンプレート |
| **セルフサービスカタログ** | IaC テンプレートライブラリの整備・公開 | テンプレートカタログ |
| **標準化推進** | 命名規則、タグ戦略、ADR の標準化 | 標準ガイドライン集 |
| **チーム間調整** | 各チームの競合解決、意思決定支援 | 調整議事録、ADR |
| **成熟度向上** | クラウド成熟度評価、改善ロードマップ | 成熟度評価レポート |
| **プラットフォーム進化** | 新技術評価、テンプレート自動更新 | テクノロジーレーダー |

#### 必要スキルセット

- **必須**: Azure Landing Zone、IaC（Bicep/Terraform）、Azure Policy、プラットフォームエンジニアリング
- **推奨**: DevSecOps、SRE 原則、アーキテクチャパターン（Well-Architected Framework）
- **資格**: AZ-305（Azure Solutions Architect Expert）、AZ-400（DevOps Engineer Expert）

#### 推奨人員構成

| 役割 | 人数 | 主な責任 |
|---|---|---|
| **CCoE リード** | 1名 | チーム統括、ステアリング会議主導 |
| **プラットフォームエンジニア** | 2〜3名 | Landing Zone、IaC テンプレート管理 |
| **セキュリティアーキテクト** | 1名 | セキュリティ標準、ゼロトラスト推進 |
| **ガバナンスエンジニア** | 1名 | Policy as Code、コンプライアンス自動化 |
| **DevOps/自動化エンジニア** | 1〜2名 | セルフサービス自動化、パイプライン |
| **合計** | **6〜8名** | |

## 4. RACI マトリックス

### 凡例

| 記号 | 意味 | 説明 |
|---|---|---|
| **R** | Responsible（実行責任）| タスクを実際に実行する担当者 |
| **A** | Accountable（説明責任）| 成果物の最終責任を持つ人物。一人のみ |
| **C** | Consulted（協議対象）| 意見・情報を提供する（双方向コミュニケーション） |
| **I** | Informed（情報受領）| 結果を通知される（一方向コミュニケーション） |

### チーム略称

| 略称 | チーム |
|---|---|
| **STR** | Cloud Strategy Team |
| **ADO** | Cloud Adoption Team |
| **GOV** | Cloud Governance Team |
| **CCE** | Cloud Center of Excellence |
| **OPS** | Cloud Operations Team |
| **SEC** | Cloud Security |

### RACI マトリックス（主要タスク・成果物）

| タスク / 成果物 | STR | ADO | GOV | CCE | OPS | SEC |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| **① クラウド戦略の策定** | **A/R** | C | C | C | I | C |
| 　├ ビジネスケース・ROI 分析 | **A/R** | I | C | I | I | I |
| 　├ クラウド導入ロードマップ | **A/R** | C | C | C | I | C |
| 　└ KPI・成果指標の定義 | **A** | R | R | R | R | R |
| **② Landing Zone の設計・構築** | I | C | C | **A/R** | C | C |
| 　├ サブスクリプション設計 | I | C | C | **A/R** | I | C |
| 　├ ネットワーク設計・実装 | I | C | I | **A/R** | C | C |
| 　├ ID 管理設計（Entra ID） | I | C | C | **A/R** | I | **R** |
| 　└ Landing Zone テンプレート管理 | I | R | C | **A/R** | I | C |

## 5. エスカレーションパス

### 意思決定の権限と範囲

| 意思決定レベル | 権限者 | 対象範囲 | 応答 SLA |
|---|---|---|---|
| **レベル 0: 自律判断** | 各チームメンバー | 標準手順範囲内の技術作業 | 即時 |
| **レベル 1: チームリード** | 各チームリード | 標準外だが低リスクの変更 | 24時間以内 |
| **レベル 2: CCoE** | CCoE リード | クロスチーム影響のある変更 | 48時間以内 |
| **レベル 3: 戦略チーム** | 戦略オーナー | 予算・スコープ・優先順位変更 | 5営業日以内 |
| **レベル 4: 経営層** | CxO | 組織変革・重大リスク・戦略転換 | 都度調整 |

```

                          技術    ポリシー  セキュリティ

                        platform  gov    security
                                      │
                                      │(戦略・予算影響あり)
                                      ▼
                             Cloud Strategy Team
                                      │
                                      │(組織・重大リスク)
                                      ▼
                                   経営層
```

【インシデント発生時のエスカレーション】

  インシデント検知
       │
       ▼

       │

### 意思決定フレームワーク（DACI）

重要な意思決定には以下のフレームワークを適用します。

| 役割 | 英語 | 説明 |
|---|---|---|
| **D - Driver** | 推進者 | 意思決定プロセスを推進し、会議を主導する |
| **A - Approver** | 承認者 | 最終決定権を持つ（一人のみ） |
| **C - Contributor** | 貢献者 | 情報・意見・専門知識を提供する |
| **I - Informed** | 通知対象 | 決定内容を通知される |

| **リソース最適化率** | Advisor コスト推奨の対応率 | Ph2: 60% / Ph3: 80% | Azure Advisor |
| **コスト予測精度** | 予測と実績の乖離率 | Ph3: ± 5% 以内 | Cost Management + カスタムレポート |
| **コスト可視化カバレッジ** | タグ付きリソースの割合 | Ph1: 80% / Ph2: 95% / Ph3: 99% | Resource Graph クエリ |

#### 運用指標（Operations）

| KPI | 説明 | 目標値 | 測定方法 |
|---|---|---|---|
| **SLO 達成率** | 定義された SLO の達成率 | 99.9% | Azure Monitor / SLO ダッシュボード |
| **可用性（稼働率）** | 重要サービスの稼働率 | 99.9%（月次） | Application Insights |
| **インシデント再発率** | 同一根本原因の再発率 | < 10% | インシデント管理システム |
| **変更成功率** | 計画通り完了した変更の割合 | > 95% | 変更管理ログ |

#### 人材・文化指標（People & Culture）

| KPI | 説明 | 目標値 | 測定方法 |
|---|---|---|---|
| **クラウド認定資格保有率** | Azure 認定取得エンジニアの割合 | Ph2: 40% / Ph3: 60% | トレーニング管理システム |
| **トレーニング完了率** | 必須トレーニングの修了率 | > 80% | LMS（学習管理システム）|
| **クラウドチャンピオン数** | 各部門のクラウドチャンピオン数 | 全部門に最低 1名 | CCoE 台帳 |
| **ワークロードチーム満足度** | 四半期アンケートスコア | > 4.0 / 5.0 | 定期アンケート |
| **セルフサービス利用満足度** | カタログ利用者の満足度 | > 4.0 / 5.0 | カタログ内フィードバック |
